# Release Notes - v0.2.0

## Overview

pgutil is the new name of this module, formerly `github.com/grokify/godb`,
and it is now PostgreSQL only. This release adds what a deploy tool needs to
put several applications on one PostgreSQL server safely: a provisioning
script for their databases and roles, a check that the server matches it,
and password verifiers so plain passwords never reach the server. None of
it needs a database driver.

## Highlights

- **`provision`:** an idempotent `psql` script that provisions databases with owner and app roles, connection limits, timeouts and per-database `CONNECT` isolation, run as a managed server's non-superuser admin, and a query that verifies the server against the plan
- **`scram`:** SCRAM-SHA-256 verifiers, so a role's password never reaches the server, its logs or its statistics in plain text
- **No driver:** identifiers, literals, `postgres://` URLs and SQLSTATE codes in the root package, usable with pgx, `database/sql` or `psql`

## Upgrading from godb

The module path changed, so this is a breaking release.

| Before | After |
|---|---|
| `github.com/grokify/godb` | `github.com/grokify/pgutil` |
| `github.com/grokify/godb/pgutil` (go-pg helpers) | `github.com/grokify/pgutil/gopg`, deprecated |

```bash
go get github.com/grokify/pgutil@v0.2.0
```

Code using the go-pg helpers changes only its import:

```go
import "github.com/grokify/pgutil/gopg"
```

go-pg is in maintenance mode, so `gopg` is deprecated and will be removed in
a later release. Existing versions of `github.com/grokify/godb` keep
working where they are pinned.

## Provisioning a Shared Server

Each database gets an owner role, which owns it and runs migrations, and an
optional app role, which the application connects as. `CONNECT` is revoked
from `PUBLIC`, so each role reaches only its own database: on a managed
server, where `pg_hba.conf` cannot be edited, these grants are the boundary
between applications.

```go
ownerV, err := scram.Verifier(ownerPassword)
appV, err := scram.Verifier(appPassword)

plan := provision.Plan{
    Databases: []provision.Database{{
        Name:  "shop",
        Owner: provision.Role{Name: "shop_owner", Verifier: ownerV},
        App: &provision.Role{Name: "shop_app", Verifier: appV,
            ConnectionLimit: 20, StatementTimeout: "30s", IdleInTransactionTimeout: "60s"},
    }},
    Lockdown:  []string{"admin_db"},
    Reachable: []string{"postgres", "template1"},
}

script, err := plan.Script(provision.ScriptOptions{}) // psql, as the server's admin
check, err := plan.VerifySQL()                        // no rows: the server matches
```

The script:

- runs as a managed server's admin, which is not a superuser, so it never sets `SUPERUSER`, `REPLICATION` or `BYPASSRLS`; `VerifySQL` checks them;
- creates what is missing and resets the rest, so it can run again at any time;
- revokes and grants as the database's owner, since only a grant's grantor can revoke it;
- gives an owner `ADMIN OPTION` on its app role, so a migration can reset the app role's password (PostgreSQL 16 or later);
- with `ScriptOptions{Redact: true}`, shows the plan for review without the verifiers.

`VerifySQL` reports each difference: a missing database or role, a wrong
owner, a privileged role, a changed connection limit or timeout, `PUBLIC`
able to connect, and any role able to reach a database other than its own.

## Tests

An opt-in integration test starts a throwaway PostgreSQL server and
provisions two applications as a non-superuser admin, checking that the
script is idempotent, that each application is kept out of the other's
database, that an owner can reset its app role's password, and that drift
is reported:

```bash
PGUTIL_INTEGRATION=1 PGUTIL_PG_BIN=/path/to/postgresql/bin go test ./...
```
